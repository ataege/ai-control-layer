# Preparation record

Date of preparation: **2026-10-02**.

This record describes the starter baseline as it stood before the implementation phase began. It is
not updated as product work lands; use the git history and [architecture.md](architecture.md) for
that.

This record states what was built before the event, how it was produced, which third-party
resources it uses, what was verified and what was deliberately left out.

## What was built

A generic monorepo starter with no product functionality:

- **Web app** (`apps/web`): application shell, three pages (home, component showcase, service
  diagnostics), a typed fetch helper, and a server-side proxy limited to three health and
  diagnostics paths.
- **Shared UI** (`packages/ui`): shadcn/ui primitives, seven generic components (AppShell,
  PageHeader, EmptyState, LoadingState, ErrorState, ConfirmDialog, CopyButton) and the Tailwind
  theme.
- **API** (`apps/api`): validated configuration, liveness and readiness, gateway diagnostics,
  database wiring without entities, migration commands, request ids, logging, a shared error
  envelope, Swagger for the three routes, and an authentication extension point that fails
  explicitly.
- **Gateway** (`services/gateway`): configuration validation, HTTP server with timeouts, structured
  logging, request ids, panic recovery, connection pool, liveness, readiness and a token-protected
  ping.
- **Contracts** (`packages/contracts`): TypeScript types, JSON Schemas, fixtures and matching Go
  DTOs with consistency tests.
- **Configuration** (`packages/config`): shared TypeScript, ESLint and Prettier settings.
- **Infrastructure** (`infra`): a Compose file for PostgreSQL and the full-container profile, a
  debug override and three Dockerfiles.
- **Scripts** (`scripts`): setup, Compose wrapper, development runner, environment wrapper,
  verification, smoke test, instruction check.
- **Team material**: `AGENTS.md` and `CLAUDE.md` (identical), six Claude Code project agents, this
  documentation.

No entities, migrations, tables, seed data, user model or authentication flow exist.

## How it was produced

- The starter was written with AI assistance, using Claude Code, on 2026-10-02.
- The shadcn/ui component sources in `packages/ui/src/components` were generated by the shadcn CLI
  4.21.1 (style `radix-nova`) and reformatted with the repository's Prettier configuration. The
  generic components in the same directory were written for this starter on top of them.
- Everything else (application code, scripts, Compose files, Dockerfiles, tests, documentation) was
  written for this starter. Apart from the shadcn/ui component source, no third-party source is
  vendored in the repository.
- Dependencies are installed from the public npm registry and the Go module proxy and are locked
  in `pnpm-lock.yaml` and `services/gateway/go.sum`.

## Review round

After the verification above, an adversarial review looked at the starter through several lenses.
Each finding was checked by a second, independent pass before it counted. Result: **26 confirmed
issues, none critical or high, 3 medium**, the rest low. All 26 were addressed on the same day:

- **Secrets on the host (medium).** `pnpm dev` passed the service token and the database password
  to the web process. The development runner now removes `GATEWAY_SERVICE_TOKEN` and every
  `POSTGRES_*` variable from the web child, and `.dockerignore` excludes `.env` files at any depth.
  A `.next/dev` cache written before the fix can still contain the old values: on a machine where
  `pnpm dev` ran earlier, delete `apps/web/.next` and consider generating new secrets.
- **API readiness (medium).** A readiness check that timed out kept its connection, so ten silent
  connection drops exhausted the pool and readiness stayed at 503. The check now uses a dedicated
  connection and discards it on failure. Also fixed: an oversized body is answered with 413
  `payload_too_large` instead of 500, the OpenAPI bounds were tightened to the contract schema, the
  database connection retries have tests, and `pnpm deploy` for the API image copies the compiled
  output and production dependencies only (checked with `pnpm deploy`, not with Docker).
- **Documentation and instructions (medium).** At review time the root README and `docs` were not
  written yet, and `AGENTS.md` still carried a placeholder for the verification status. Both exist
  now, `pnpm check:instructions` fails on the placeholder, and the ownership map covers
  `.env.example`, the root ignore files, `db/migrations`, `README.md` and `docs`.
- **Timeouts and gateway configuration.** `DATABASE_TIMEOUT_MS` and `GATEWAY_TIMEOUT_MS` accept
  100-20000 ms in both backends. The gateway cancels in-flight readiness pings on shutdown, rejects
  blank required values and a token padded with whitespace, and trims the bind variables in
  `-healthcheck`.
- **Development runner and images.** The gateway `dev` script compiles `bin/gateway-dev` and runs
  it directly, so the runner's forced stop reaches it. The API and gateway images set their own
  `0.0.0.0` bind address.
- **Web and UI.** The mobile menu no longer blocks the page after the window is widened; `start`
  serves the standalone build through a Node launcher (new optional `WEB_HOST`); the showcase has
  one `h1` and section headings; ConfirmDialog reports Escape as cancel; the gateway cards label
  the status of the diagnostics response as such.
- **Contract checks and wording.** The TypeScript samples are compared with the fixture files, the
  Go tests compare the emitted values with the fixtures, and statements that claimed more than the
  tests guard were narrowed. A few abbreviated identifiers were renamed and missing intent comments
  added.

Re-checked afterwards: `pnpm verify` with Go on `PATH` passed 6 of 6 (tests: contracts 5, web 25,
API 36, gateway 5 Go packages); the development runner started all three services and `pnpm smoke`
passed 19 of 19 with the database up; each owner ran targeted live checks for its fix. The README
section "Verification status" lists them. A final pass from a clean state (frozen install, fresh `.env`, empty database) then repeated the database-down sequence, the migration commands, the table listing and the secret scans with the same results. Only the browser view of the diagnostics page was not repeated. Still not run at
all: Docker, Compose, the image builds and full-container mode, including the Dockerfile and
`.dockerignore` changes from this round.

One incident during the round: a `pnpm deploy --prod` test in the live workspace left pnpm's
recorded install state production-only for a short time, and the next `pnpm` scripts aborted with
`ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`. Nothing was removed and the lockfile is unchanged.
Run such deploy checks from a copy of the workspace.

## Recorded decisions and deviations

| Topic                  | Decision                                                                                                                                                                                                                                                                                                   |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript             | 6.0.3, not 7.0.2: typescript-eslint 8.71 requires `<6.1` and `@nestjs/swagger` 12 requires `^5.5 \|\| ^6`.                                                                                                                                                                                                 |
| ESLint                 | 10.11.0, because ESLint 9 is flagged unsupported upstream. `eslint-plugin-react` 7.37.5 (pulled in by `eslint-config-next`) crashes on ESLint 10 when the React version is auto-detected, so `packages/config/eslint/next.mjs` pins `settings.react.version`. pnpm prints peer warnings for those plugins. |
| NestJS module format   | NestJS 12 is ESM-only; the API is `"type": "module"` with `nodenext`.                                                                                                                                                                                                                                      |
| Test runner            | Vitest replaces Jest in both TypeScript apps (the NestJS 12 scaffold default).                                                                                                                                                                                                                             |
| TypeORM CLI            | TypeORM 1.1.1 CLI runs through `typeorm-ts-node-esm` (ts-node 10.9.2).                                                                                                                                                                                                                                     |
| Migration location     | **Deviation from the requested layout.** Migrations live in `apps/api/src/database/migrations`, not in `db/migrations`: migration classes outside the API package fail `tsc` (TS6059, rootDir) and cannot resolve `typeorm` under pnpm. `db/migrations` holds a README and a `.gitkeep` explaining this.   |
| shadcn/ui              | Style `radix-nova` (Radix flavour), generated with shadcn CLI 4.21.1. Components use the `cn` package (0.4.0), as the current CLI emits.                                                                                                                                                                   |
| Versions held back     | turbo 2.11.6 rather than 2.11.7 and `@types/node` 24.19.0 rather than 24.19.1, because pnpm 11 rejects releases younger than one day (`minimumReleaseAge`). pnpm added `minimumReleaseAgeExclude` entries for `lucide-react@1.50.0` and `supertest@7.3.1`.                                                 |
| pnpm version           | 11.10.0 pinned through `packageManager` (the version on the preparation machine). Newer 11.x and 12.x releases exist.                                                                                                                                                                                      |
| Setup command          | Bare `pnpm setup` is a pnpm built-in that edits the shell profile; the starter's command is `pnpm run setup`.                                                                                                                                                                                              |
| PostgreSQL data path   | The PostgreSQL 18 image stores data under `/var/lib/postgresql`; the named volume is mounted there.                                                                                                                                                                                                        |
| Published ports        | Published container ports bind to `127.0.0.1`. The gateway is not published in full-container mode unless `--debug` is passed (`infra/compose.debug.yaml`).                                                                                                                                                |
| Go toolchain in checks | Gateway Turborepo tasks are uncached on purpose so that a missing Go toolchain is never reported as a cached pass.                                                                                                                                                                                         |
| Timeout range          | `DATABASE_TIMEOUT_MS` and `GATEWAY_TIMEOUT_MS` accept 100-20000 ms in the API and the gateway, so one `.env` value is valid for both and a readiness answer fits inside the gateway's 30 s write timeout.                                                                                                  |
| Gateway in development | `pnpm dev:gateway` compiles `bin/gateway-dev` and runs it instead of `go run`, so the service is a direct child that stop signals reach. There is no hot reload.                                                                                                                                           |
| Web launchers          | The web `dev` and `start` scripts are Node launchers without shell syntax. `start` runs the standalone server and binds to `WEB_HOST` (default `127.0.0.1`), an optional variable that is not in `.env.example`; an inherited `HOSTNAME` is ignored because shells may export the machine name there.      |
